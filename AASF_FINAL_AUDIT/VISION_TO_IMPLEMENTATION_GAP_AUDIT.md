## 1. Executive Summary: Vision vs. Reality

The original project vision for the **Adaptive Agentic Security Firewall (AASF)** was to establish an authoritative, in-process runtime security mediator positioned between autonomous, tool-using AI agents and their underlying execution backends. 

### The Core Research Question
The central motivating research direction was formulated as:
> **RQ-0:** *Can contextual information — including prior actions, permissions, resource sensitivity, and observable workflow state — improve the detection and prevention of multi-step threats compared with independent per-action risk assessment, while maintaining acceptable false-positive rates and decision latency?* (`docs/00_RESEARCH_FOUNDATION.md` §5.1, `docs/09_DECISIONS_AND_OPEN_QUESTIONS.md` §D-10b)

Operationalized under:
> **RQ-1:** *How do action-only, transcript-based, deterministic stateful, and hybrid/cascade-based permission monitors compare in terms of malicious-action prevention, benign-task completion, human-review burden, and decision latency for multi-step AI-agent workflows?* (`docs/00_RESEARCH_FOUNDATION.md` §5.2, `docs/09` §D-10)

### The Architectural Verdict
Our forensic audit establishes a critical divergence between the project's **enforcement architecture (Track A)** and its **empirical research pipeline (Track B)**:

1. **Track A (Deterministic Permission Enforcement & State Tracking): SUBSTANTIALLY IMPLEMENTED & VERIFIED**
   - The deterministic policy engine (`PolicyEngine`, rules R1–R5), observable state fold ($\Phi(H_t, \text{Reg})$), cryptographic single-use token issuance (`TokenStore`), and controlled execution gateway (`ControlledExecutor`) are cleanly built in Python and verified by 262 automated test cases.
   - Hard policy prohibitions (`PROHIBIT`) unconditionally dominate execution paths (INV-01, INV-03).
   - In-memory state-head hash chaining with RFC 8785 canonical JSON bytes guarantees tamper-evident state progression (INV-12).

2. **Track B (Contextual Multi-Step Semantic Risk Detection): DISCONNECTED & UNPROVEN**
   - The runtime execution monitors (`TranscriptMonitor`, `HybridMonitor` in `src/firewall/monitor/`) were constructed as isolated modules, but **were never integrated into an automated, end-to-end multi-step experiment runner**.
   - The core experiment execution files `experiments/run_experiment.py` and `experiments/evaluate.py` are **0-byte empty files**.
   - The imported experimental results (`experiments/results/results_full_study.csv` [N=2,790] and `ablation_results.csv`) were generated by an external ad-hoc script (`experiments/scripts/adaptive_security_test.py`) calling local Ollama endpoints directly. **This script evaluates prompt-injection detection on single-turn requests; it completely bypasses the firewall runtime, does not import `firewall.core`, tracks no state, and evaluates zero multi-step workflows.**
   - Shrishti's exploratory pilot (`docs/research/shrishti/runtime-risk-experiment/`) revealed that when an LLM monitor (`gpt-4o-mini`) was tested on a 72-case synthetic multi-step benchmark, it suffered a **100% false positive rate (27/27)** on distributed negative workflows because it hallucinated that prior selection of a confidential resource permanently tainted downstream benign exports. Meanwhile, the post-hoc deterministic stateful firewall (B6) achieved 100% accuracy (72/72) with zero latency.
   - **Conclusion on Core Research Claim:** AASF does **not** demonstrate that contextual LLM risk monitoring outperforms action-level detection. In reality, the codebase demonstrates that **deterministic stateful policy rules solve the benchmark completely, whereas contextual LLMs experience severe context rot and false-alarm saturation.**

## 4. Evaluation of the Central Research Contribution

We systematically addressed the ten audit questions regarding contextual threat detection:

1. **Does the runtime preserve relevant action history?**  
   *Yes.* `SessionState` maintains `selected_resources`, `jobs`, `destination`, and cumulative `egress_counters` across successive actions within an active session.
2. **Does the semantic monitor receive meaningful historical context?**  
   *Partially.* `TranscriptMonitor` receives serialized textual history via `format_transcript()`, and `HybridMonitor` receives allow-listed `state_summary`. However, this data was evaluated only in isolated pilot scripts, never in the full integrated firewall experiment runner.
3. **Does the monitor understand relationships between successive actions?**  
   *No.* Pilot evidence shows that the LLM monitor treated historical resource selection as a permanent taint, misclassifying all 27 distributed negative workflows as unsafe (100% False Positive Rate).
4. **Can it detect suspicious action sequences where individual actions appear benign?**  
   *Yes, but via deterministic policy, NOT the semantic monitor.* The multi-step sequence `select_resource(CONFIDENTIAL) -> create_export_job() -> configure_destination(EXTERNAL) -> execute_export()` is successfully blocked at the fourth step by deterministic Rule R1, because $S_t$ tracks the bound resource and destination zone.
5. **Does it consider task intent, resource sensitivity, provenance, and context?**  
   *Yes.* `Registry` provides authoritative classifications (`CONFIDENTIAL`, `PUBLIC`) and destination zones (`INTERNAL`, `EXTERNAL`). Provenance tags (`GATEWAY`, `REGISTRY`, `TOOL_TYPED`) prevent agent text from injecting trusted attributes.
6. **Can it distinguish an isolated harmless operation from a suspicious multi-step trajectory?**  
   *Yes, through the state fold.* A standalone `execute_export()` to an internal zone is permitted; the same tool called on a confidential dataset bound to an external destination is blocked.
7. **Does contextual information influence risk assessment in a measurable way?**  
   *In the policy engine, yes.* In the semantic LLM monitor, contextual history caused severe performance degradation (false positive saturation).
8. **Does the final decision engine use contextual information appropriately?**  
   *Yes.* The combinator `decide()` correctly applies D1–D5. Under default `monitor_authority="decide_undetermined"`, an advisory monitor verdict can only grant access if policy is `UNDETERMINED` and the tool is outside mandatory review classes.
9. **Can the system detect attacks that a permission-only baseline misses?**  
   *No evidence exists to support this.* The deterministic stateful baseline (B6) blocked 100% of the attacks in the benchmark. The LLM monitor added zero additional detection capability while introducing massive false alarm rates.
10. **Are contextual detection claims supported by experimental results?**  
    *No.* The experimental CSVs in the repository (`results_full_study.csv`) evaluate single-turn prompt injection via Ollama, not multi-step contextual workflows.

## 6. Vision Gap Verdict & Required Remediation

### Classified Gaps

#### Category 1: Critical to Security (Must fix before deployment)
1. **SEC-GAP-01: Review Approval Policy Bypass:** `FirewallCore.resolve_review()` does not re-evaluate `PolicyEngine.evaluate()` or verify that current `state.head_hash` matches ticket creation state before issuing execution tokens. Human approval can execute newly prohibited or stale actions.
2. **SEC-GAP-02: Advisory Monitor Permission Elevation (Branch D5b):** Under default configuration `DecisionConfig(monitor_authority="decide_undetermined")`, a compromised monitor emitting `BENIGN` converts an `UNDETERMINED` action into `ALLOW` for all tool classes except `DESTRUCTIVE` and `PRIVILEGED_ADMIN`.

#### Category 2: Critical to Original Vision & Research
1. **RES-GAP-01: Missing End-to-End Experiment Harness:** `experiments/run_experiment.py` and `evaluate.py` are empty 0-byte stubs. The repository lacks a unified script to evaluate arms B0–B6 and P1 under identical conditions.
2. **RES-GAP-02: Disconnected Rejection Cascade:** The Ollama cascade experiments in `experiments/scripts/adaptive_security_test.py` operate completely outside `FirewallCore`.
3. **RES-GAP-03: Unsupported Research Claims:** Research paper drafts (`SHRISTI_RP.md`, `AKSHAT_RP.md`) report findings that must be clearly qualified as pilot-study observations on synthetic data, not proven production capabilities.

#### Category 3: Important to Performance & Reliability
1. **PERF-GAP-01: In-Memory Only Audit & State Persistence:** `AuditStore` and `FirewallCore._states` reside in process RAM. A process crash loses all session states and audit chains.
2. **PERF-GAP-02: Empty YAML Configuration Files:** All files in `config/` are 0 bytes. System relies on hardcoded Python instantiation.
